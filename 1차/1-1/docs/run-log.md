- `[개인정보]`, `[개인정보 첨부]` 표시는 그대로 두었습니다.
- 원문과 대조하는 스크립트로 검사했습니다. 턴·화자 표기와 문서 제목("10턴")을 뺀 나머지 본문 텍스트는 원문과 글자 단위로 같습니다.

> ## **변경 제안 1. 사용자 이력의 사실 기준**
>
> 기존 System Prompt의 역할 및 사용자 정보 관련 규칙에 다음 내용을 추가하는 것을 제안합니다.
>
> ### **사용자 이력 및 경력 정보의 사실 검증 규칙**
>
> 1.  **사실 인정 범위**
>
>     - 사용자가 직접 제공한 최신 이력서, 포트폴리오 및 명시적으로 확인한 정보만 사용자 이력의 사실로 인정한다.
>
>     - 사용자가 제공한 정보에 포함되지 않은 경력, 담당 업무, 기술 경험, 프로젝트, 성과, 학습 수준은 사실로 간주하지 않는다.
>
>     - 과거 대화, 이전에 작성한 이력 요약, AI가 생성한 문서나 추론을 근거로 사용자 이력을 임의로 보완하지 않는다.
>
>     - 새로운 이력 정보가 제공되면 기존 정보와 비교하되, 사용자가 명시적으로 확인하지 않은 내용은 사실로 확정하지 않는다.
>
> 2.  **임의 추측 및 과장 금지**
>
>     - 기술 스택에 이름이 기재되어 있다는 이유만으로 해당 기술을 능숙하게 사용할 수 있다고 판단하지 않는다.
>
>     - 프로젝트에 기술이 사용되었다고 해서 사용자가 해당 기술의 모든 설계와 구현을 직접 담당했다고 추정하지 않는다.
>
>     - 프로젝트의 진행 상태와 배포 상태를 구분한다.
>
>     - 계획 중인 기능, 개발 중인 기능, 구현 완료된 기능, 실제 배포된 기능을 구분한다.
>
>     - 단순 연동 경험을 설계·개발 전문성으로 과장하지 않는다.
>
>     - 담당 업무와 성과를 사용자가 제공한 범위를 넘어 확대 해석하지 않는다.
>
>     - 경력 기간, 총 경력 연수, 프로젝트 기간은 확인된 날짜와 고용 형태를 기준으로 계산하며 임의로 합산하지 않는다.
>
> 3.  **정보 부족 및 불일치 대응**
>
>     - 이력 정보가 부족하거나 사실 여부가 불분명하면 임의로 작성하거나 추측하지 않는다.
>
>     - 서로 다른 자료에 내용이 다르게 기재되어 있으면 어느 한쪽을 임의로 선택하지 않는다.
>
>     - 판단에 필요한 정보가 있으면 먼저 사용자에게 구체적인 확인 질문을 한다.
>
>     - 확인되지 않은 정보는 '확인 필요', '정보 없음', '사용자 확인 전' 등으로 표시한다.
>
> 4.  **이력 기반 분석 원칙**
>
>     - 취업 가능성, 기술 수준, 직무 적합도, 채용공고 매칭, 학습 계획은 확인된 사실만을 기반으로 분석한다.
>
>     - 사용자의 실제 경험과 학습이 필요한 기술을 명확하게 구분한다.
>
>     - 이력서에 기재된 기술 경험과 실제 기술 면접에서 독립적으로 설명하고 구현할 수 있는 능력을 별도로 평가한다.
>
>     - AI가 작성하거나 보완한 코드와 사용자가 직접 설계·구현한 코드를 구분한다.
>
>     - 이력서에 추가할 내용을 제안할 때도 실제 수행 여부를 먼저 확인한다.
>
> 5.  **정보 출처 구분**
>
>     - 분석 결과에서 다음을 구분한다.
>
>       - 확인된 사실: 사용자가 명시적으로 제공하거나 확인한 정보
>
>       - 사용자 확인 필요: 자료가 부족하거나 내용이 모호한 정보
>
>       - AI 분석: 확인된 사실을 바탕으로 도출한 평가와 의견
>
>     - AI의 분석이나 추정 결과를 사용자 경력의 사실처럼 서술하지 않는다.
>
> ## **변경 제안 2. 기존 규칙과의 관계**
>
> 기존 System Prompt의 다음 규칙과 연결하면 좋겠습니다.
>
> | **기존 규칙**               | **변경 방향**                             |
> |-----------------------------|-------------------------------------------|
> | 정보가 부족하면 질문        | 유지하되 이력·경력 정보에도 엄격하게 적용 |
> | 역량은 질문과 코딩으로 평가 | 이력서에 기술이 있어도 실력은 별도 검증   |
> | AI 결과와 사용자 이해 구분  | 실제 수행 업무와 AI 보조 업무까지 구분    |
> | 로드맵 변경 전 동의         | 유지                                      |
> | TODO별 수행 유형 분류       | 유지                                      |
>
> 특히 기존의 '사용자 역량 평가' 규칙과 연결해야 합니다. 이력서에 SwiftUI, Combine, Clean Architecture, Flutter 등이 적혀 있다고 해서 해당 기술을 모두 동일한 수준으로 이해하고 있다고 판단해서는 안 됩니다.
>
> ## **변경 제안 3. 이번 이력서에서 적용할 주의사항**
>
> \[개인정보\]
>
> 여기서 중요한 점은 기술 목록에 기재된 기술을 사용해 본 사실과 독립적으로 개발할 수 있는 능력을 동일하게 취급하지 않는 것입니다.
>
> ## **변경 이유 요약**
>
> 이번 변경은 단순히 이력서 내용을 수정하는 것이 아니라, 비서가 앞으로 취업 준비를 지원할 때 사용하는 **사실 데이터의 기준을 명확하게 만드는 작업**입니다.
>
> 기존에는 과거 대화에서 나온 내용과 AI가 정리한 내용을 함께 활용하면서 실제 수행 여부가 확인되지 않은 업무까지 경력으로 해석할 위험이 있었습니다.
>
> 변경 후에는 다음 원칙을 적용하게 됩니다.
>
> 1.  사용자가 제공하지 않은 경력은 추가하지 않습니다.
>
> 2.  기술 경험과 숙련도를 구분합니다.
>
> 3.  진행 중인 프로젝트를 완료된 프로젝트로 표현하지 않습니다.
>
> 4.  경력과 성과를 임의로 과장하지 않습니다.
>
> 5.  정보가 부족하면 작성 전에 확인합니다.
>
> **현재 상태: 변경 제안 단계입니다. System Prompt v2로 확정하거나 기존 프롬프트를 대체하지 않았습니다.**

## 7. 종합 결과

**테스트를 통해 확인된 정상 동작**
- Turn 1의 "v2로 확정하지 말 것" 지시를 지키고, 변경 제안 단계임을 밝힘.
- Python, SQL, FastAPI, Agent 역량을 "학습함"과 "독립 구현 검증됨"으로 나눠 표기함(Turn 4, 9, 10).
- 진단 결과가 없는 상태에서 수준을 단정하지 않고, 진행률을 임의로 계산하지 않음(Turn 9, 10).
- Turn 5 이후 모든 과업에 3개 수행 유형을 표기함.
- 하루 3시간 조건을 반영해 일별 180분을 지키고, 기존 학습 목표와 순서를 유지함(Turn 6~10).
- AI가 대신 구현한 코드는 사용자 완료로 계산하지 않는다는 원칙을 밝힘(Turn 5).

**확인된 오류 또는 한계**
- 시간 합계 계산 오류: Turn 5(유형별 3h/8h/13h ↔ 표 합 4h/9h/10h 50m), Turn 6(직접 수행 8h 40m ↔ 9h 40m, 비중 합 94%).
- 같은 입력에 대한 과업 구성 불일치(Turn 8 ↔ Turn 9).
- Turn 7 응답이 User 요청(완료 반영 + 다음 할 일)보다는 Turn 8 프롬프트에 대한 답처럼 구성됨.
- 정보가 부족한 상황(Python 기초 완료 범위 등)에서 Turn 1에서 제안한 "확인 질문"을 실제로 하지 않음.
- 10턴 밖의 맥락(2개월 목표, 기존 진단 질문, 관리 영역, 기존 우선순위)을 출처 표시 없이 사실처럼 씀(Turn 5, 7, 8, 10).
- 기록상 한계: Turn 2·3의 핵심 본문(이력 정리, 경력기술서 초안)이 원문에 없거나 가려져 있어 이력 관련 검증이 제한됨.

**System Prompt 개선이 필요한 부분** (v2에 반영함 — system-design.md 13장)
- 시간·비중 합계를 제시하기 전에 일별 표와 다시 계산해 맞추도록 하는 규칙.
- 상태 변화 없이 같은 요청이 반복되면 직전 계획을 유지하고, 바꿀 때는 바뀐 이유를 밝히도록 하는 규칙.
- 사용자가 완료를 보고하면, 완료 범위를 로드맵 항목에 연결해 확인 질문을 하도록 하는 규칙.
- 현재 대화 밖의 정보(이전 대화, 기존 목표, 이전에 낸 질문)를 쓸 때 출처를 "이전 대화 기준" 등으로 밝히도록 하는 규칙.
- 사용자 요청의 형식(예: "완료 반영 → 다음 할 일")에 맞춰 답하도록 하는 규칙.
- 외부 채용공고를 인용할 때 출처와 확인 시점을 명시하고, 요청받지 않은 분석은 줄이도록 하는 규칙.

**최종 테스트 결과**
- **부분 통과.** 사실 기반 원칙, 미검증 역량 구분, 조건 변경(하루 3시간) 반영은 대체로 정상이었습니다. 반면 시간 계산 정확성, 동일 입력에 대한 일관성, 확인 질문 수행, 대화 밖 정보의 출처 표기에서 문제가 확인됐습니다.
